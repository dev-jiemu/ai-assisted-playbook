# CS 학습 노트 (cs-study-note)

## 목적

CS를 공부하며 Claude와 나눈 대화를 그때그때 마크다운 문서로 남기고, 사람이 직접
`git add / commit / push`를 치지 않아도 되도록 자동화합니다. 핵심은 **대화에서 실제로
다룬 내용만** 기록하는 것입니다 — 일반적으로 알려진 배경지식을 임의로 덧붙이거나,
논의하지 않은 내용을 지어내지 않습니다. 사용자가 실제로 질문하고 이해해 나간 흐름을
보존하는 것이 이 노트의 가치입니다.

## 언제 쓰는지

사용자가 방금 CS 주제(알고리즘, OS, 네트워크, DB, 시스템 디자인, 자료구조, 특정
언어/프레임워크 등)에 대해 대화를 나눈 뒤 그 내용을 정리해 달라고 하거나, 이미 정리해둔
노트에 오늘 배운 내용을 이어 붙이고 싶어할 때 이 스킬을 사용합니다.

## 작업 순서

이 순서를 그대로 따르되, 애매한 부분이 있으면 넘겨짚지 말고 사용자에게 짧게 확인하세요.

### 1. 범위 파악

무엇을 정리할지 확인합니다. 보통은 "지금까지 이 대화에서 다룬 주제"이지만, 대화가 길고
여러 주제를 넘나들었다면 어느 부분을 정리할지 짧게 확인하세요 (예: "방금 얘기한 TCP
핸드셰이크 부분만 정리할까요, 오늘 얘기한 것 전체를 정리할까요?"). 이미 이 세션에서 한
번 정리했다면, 그 이후 새로 나온 내용만 다룹니다.

### 2. 저장소 상태 확인

작업을 시작하기 전에 `git status`, `git branch --show-current`로 현재 브랜치와 변경사항을
확인합니다. 다른 미커밋 변경사항이 섞여 있다면, 이 스킬이 만드는 파일만 정확히 add해서
사용자의 다른 작업을 실수로 커밋하지 않도록 주의하세요.

### 3. 문서 위치와 파일명

대화 내용을 보고 어떤 CS 분야인지 판단해 하위 폴더를 정합니다. 저장소에 이미 존재하는
폴더 구조가 있다면 그것을 따르고, 없다면 자연스러운 카테고리 폴더를 새로 만드세요 (예:
`network/`, `os/`, `database/`, `algorithm/`, `data-structure/`, `system-design/`,
언어/프레임워크별 폴더 등). 애매하면 사용자에게 물어보거나 `misc/`에 둡니다.

파일명은 주제를 나타내는 kebab-case로 짓습니다 (예: `network/tcp-three-way-handshake.md`).

같은 주제로 이미 파일이 있는지 먼저 찾아보세요.
- 이미 있다면: 새로 만들지 말고, 그 문서 아래에 오늘 날짜 섹션을 이어 붙이는 것을
  기본으로 삼습니다 (같은 주제를 여러 번 공부하며 지식이 쌓이는 게 자연스럽기 때문에,
  학습 기록이 여러 조각으로 흩어지지 않도록 합니다). 사용자가 새 파일을 원하면
  그렇게 합니다.
- 없다면: 새 파일을 만듭니다.

### 4. 문서 작성

아래 템플릿을 기본으로 쓰되, 대화 내용에 안 맞는 섹션(예: 코드 예시가 전혀 없었던
대화)은 억지로 채우지 말고 자연스럽게 생략하세요. 형식보다 중요한 건 나중에 다시
읽었을 때 그날 무엇을 이해했는지 바로 떠오르는 기록을 남기는 것입니다.

```markdown
# [주제]

> 정리일: YYYY-MM-DD

## 개요
무엇에 대한 이야기였는지 2~3문장 요약.

## 핵심 내용
실제로 논의한 개념들. 필요하면 소제목으로 나눈다.

## 예시 / 코드
대화 중 나온 예시나 코드가 있으면 그대로 정리.

## 질문했던 것들
사용자가 궁금해했거나 헷갈려했던 포인트와 그 답. (이해 과정을 남기는 게 나중에
복습할 때 특히 유용하다.)

## 참고
대화 중 언급된 자료나 링크가 있으면.
```

기존 파일에 이어 붙이는 경우, 같은 형식으로 새 날짜 구분자(`## YYYY-MM-DD 추가 학습`
등)만 뒤에 덧붙이고 기존 내용은 건드리지 않습니다.

### 5. 초안 검토

파일에 실제로 쓰기 전에, 만든 초안을 대화창에 그대로 보여주고 의견을 구합니다. 예:
"이렇게 정리했는데 괜찮을까요? 빠진 내용이나 고칠 부분 있으면 말씀해주세요."

사용자가 수정을 요청하면 반영하고 다시 보여주세요. 이 단계를 건너뛰지 마세요 —
틀린 내용이 저장소에 그대로 커밋되면 나중에 복습할 때 오히려 해가 됩니다.

### 6. 커밋

사용자가 "커밋해줘", "좋아, 이대로 올려줘" 처럼 승인하면:

1. 파일을 실제 경로에 씁니다 (새 파일 생성 또는 기존 파일에 이어 붙이기).
2. 이 스킬이 만들거나 수정한 파일만 `git add`합니다.
3. 커밋 메시지는 conventional commit 스타일로 남깁니다: `docs: <주제> 정리` (기존
   파일에 이어 붙인 경우엔 `docs: <주제> 추가 학습 내용 정리`).
4. `--no-verify`나 서명 생략 같은 안전장치 우회는 사용자가 명시적으로 요청하지 않는
   한 하지 않습니다.

### 7. Push 전 확인

커밋 직후 바로 push하지 말고 먼저 묻습니다: "push할까요?"

- 사용자가 승인하면 `git push origin <현재 브랜치>` (이미 설정된 upstream 사용).
  upstream이 없으면 무엇을 할지 물어보세요.
- 거절하거나 응답이 없으면 커밋만 로컬에 남겨두고, 나중에 원하면 push할 수 있다고
  안내합니다.
- push가 거부되거나(non-fast-forward, protected branch, 권한 없음 등) 충돌 가능성이
  있으면, `--force`나 임의의 merge/rebase를 하지 말고 무슨 상황인지 그대로 사용자에게
  전달하고 어떻게 할지 물어보세요.

### 8. 결과 보고

작업이 끝나면 커밋 해시(짧은 형태), 브랜치명, push 성공 여부, 문서 경로를 한두
문장으로 요약해서 알려주세요.

## 주의할 점

- 이 스킬은 로컬 git 자격 증명(SSH 키 또는 `gh` 인증)이 이미 설정되어 있다는 것을
  전제로 합니다. push가 인증 오류로 실패하면 자동화를 억지로 우회하지 말고 사용자에게
  인증 상태를 확인해 달라고 안내하세요.
- 이미 존재하는 파일을 다룰 때는 기존 내용을 지우거나 무시하지 말고, 새 내용을 이어
  붙이는 방식으로 처리하세요.
- 대화에 없던 내용을 지어내서 채우지 마세요.
- 초안 검토 단계 없이 바로 커밋/push하지 마세요.
- `git add -A`로 관련 없는 변경사항까지 통째로 커밋하지 마세요.
- 충돌 상황에서 임의로 강제 push하거나 되돌리지 마세요 — 항상 사용자에게 확인하세요.
