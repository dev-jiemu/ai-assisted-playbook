# 아키텍처 설계 노트 (arch-design-note)

## 목적

아키텍처 설계를 공부하는 과정에서 나온 생각, 결정, 트레이드오프를 그때그때 마크다운 문서로 남기고, 사람이 직접 `git add / commit / push`를 치지 않아도 되도록 자동화합니다. 학습 기록이 파편화되지 않고 항상 레포지토리 안에 축적되게 하는 것이 목표입니다.

## 언제 쓰는지

사용자가 특정 아키텍처 주제(예: "이벤트 기반 주문 서비스", "캐시 무효화 전략", "마이크로서비스 간 통신 방식")를 설명하거나, 방금 논의한 설계 내용을 정리해 달라고 하거나, 다이어그램을 그려서 레포에 남기고 싶어할 때 이 스킬을 사용합니다.

## 작업 순서

이 순서를 그대로 따르되, 각 단계에서 애매한 부분이 있으면 넘겨짚지 말고 사용자에게 짧게 확인하세요.

### 1. 주제와 범위 파악

무엇에 대한 노트인지 확인합니다. 사용자가 이미 명확히 말했다면 그대로 쓰고, 방금 나눈 대화에서 설계를 논의했다면 그 내용을 근거로 삼습니다. 애매하면 "이번 노트는 어떤 설계/컴포넌트에 대한 건가요?" 정도로 짧게 물어보세요.

### 2. 저장소 상태 확인

작업을 시작하기 전에 `git status`, `git branch --show-current`로 현재 브랜치와 변경사항을 확인합니다. 다른 미커밋 변경사항이 섞여 있다면, 이 스킬이 만드는 파일만 정확히 add해서 사용자의 다른 작업을 실수로 커밋하지 않도록 주의하세요.

### 3. 문서 위치와 파일명

기본적으로 `docs/architecture/` 폴더에 저장합니다 (없으면 새로 생성). 파일명은 `YYYY-MM-DD-주제-slug.md` 형식을 사용합니다. 예: `docs/architecture/2026-08-20-event-driven-order-service.md`. 이미 같은 주제의 문서가 있다면 새로 만들지 말고 그 문서를 업데이트하세요 (학습 기록이 여러 조각으로 흩어지지 않도록).

### 4. 문서 작성

아래 템플릿을 기본으로 쓰되, 내용에 안 맞는 섹션은 자연스럽게 생략하거나 조정해도 됩니다. 형식보다 중요한 건 실제로 쓸모 있는 기록을 남기는 것입니다.

```markdown
# [주제]

## 개요
무엇을 왜 설계/학습했는지 2~4문장.

## 다이어그램
​```mermaid
(구조에 맞는 다이어그램: component, sequence, flowchart, C4 등)
​```

## 설계 결정과 트레이드오프
검토한 대안, 선택한 이유, 포기한 것과 그 대가를 정리.

## 구현 언어 후보
이 설계를 실제로 구현한다면 쓸 만한 언어들을 정리하고, 그중 하나를 추천.

| 언어 | 장점 | 단점 |
| --- | --- | --- |
| (언어명) | ... | ... |

**추천: (언어명)** — 이 설계의 어떤 특성(동시성 요구, 생태계, 팀 숙련도, 배포 환경 등) 때문에 이 언어가 적합한지 이유를 설명.

## 관련 코드
실제 레포 코드와 연결되는 부분이 있으면 파일 경로와 함께 인용.
​```language
// path/to/file.ts 참고
​```

## 다음 학습 방향 / 열린 질문
```

다이어그램은 실제로 다루는 내용(컴포넌트 구조, 요청 흐름, 상태 전이 등)에 맞는 mermaid 문법을 고르세요. 억지로 끼워맞추지 마세요.

구현 언어 후보 섹션은 이 설계를 실제로 코드로 옮길 때 선택지가 될 만한 언어 2~4개를 골라 비교합니다. 후보를 고를 때는 이 설계의 성격(동시성/처리량이 중요한지, 생태계나 라이브러리 지원이 중요한지, 팀이 이미 익숙한 스택이 있는지, 배포 환경 제약이 있는지)을 기준으로 삼고, 아무 언어나 나열하지 마세요. 이미 레포에서 쓰고 있는 언어가 있다면 반드시 그 언어를 후보에 포함하고, 새 언어를 도입하는 것과 비교했을 때의 실익을 같이 짚어주세요. 장단점은 일반론("빠르다", "생태계가 좋다")보다 이 설계 상황에 실제로 영향을 주는 이유를 쓰세요.

### 5. 커밋

파일을 저장한 뒤 해당 파일만 `git add`하고, 다음 형식으로 커밋합니다.

```
docs(architecture): <주제> 노트 추가
```

기존 문서를 업데이트한 경우엔 `추가` 대신 `업데이트`를 씁니다.

### 6. Push

`git push origin <현재 브랜치>`로 push합니다. 아래 상황에서는 강제로 밀어붙이지 말고 사용자에게 그대로 보고하세요.

- push가 거부되면 (예: non-fast-forward, protected branch, 권한 없음) — `--force`를 쓰지 말고 무슨 에러였는지 그대로 전달합니다.
- 원격에 새 커밋이 있어서 충돌 가능성이 있으면 — 임의로 merge/rebase하지 말고 사용자에게 확인을 구합니다.

### 7. 결과 보고

작업이 끝나면 커밋 해시(짧은 형태), 브랜치명, push 성공 여부, 문서 경로를 한두 문장으로 요약해서 알려주세요.

## 주의할 점

- 이 스킬은 로컬 git 자격 증명(SSH 키 또는 `gh` 인증)이 이미 설정되어 있다는 것을 전제로 합니다. push가 인증 오류로 실패하면 자동화를 억지로 우회하지 말고 사용자에게 인증 상태를 확인해 달라고 안내하세요.
- 이미 존재하는 파일을 덮어쓸 때는 기존 내용을 무시하지 말고, 새 내용을 이어붙이거나 병합하는 방식으로 처리하세요.
- 이 스킬의 목적은 "빠른 기록"입니다. 지나치게 형식적이고 장황한 문서보다는, 나중에 다시 읽었을 때 그날 무엇을 공부하고 결정했는지 바로 이해되는 글을 우선하세요.
