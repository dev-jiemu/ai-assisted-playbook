# Architecture Intent & Tradeoff Analysis Skill

사용자가 지정한 코드베이스, 특정 클래스, 모듈 또는 시스템 구조의 **설계 의도(Rationale)**를 역추적하고 종합 보고서를 작성합니다.

## 분석 가이드라인

1. **추측 억제 & 근거 기반 문서 작성**:
   - 코드 내 주석, Git 커밋 로그, PR 맥락, 설정 파일, 인터페이스 분리 구조를 근거로 사용합니다.
   - 확실한 근거가 부족한 가설은 `⚠️ 가설/추정` 레이블을 명시합니다.

2. **산출물 경로**:
   - 결과물은 프로젝트 루트 기준 `docs/architecture/` 하위에 `YYYYMMDD-[대상이름]-intent.md` 형식으로 저장합니다. (`/tmp` 사용 금지)

---

## 작성 문서 구조 (템플릿)

문서 작성 시 다음 구조를 반드시 준수합니다:

### 1. 개요 및 배경 (Context)
- 분석 대상: [파일/모듈/클래스 경로]
- **핵심 문제 의식**: 이 설계는 원래 어떤 기술적/비즈니스적 문제를 해결하기 위해 도입되었는가?

### 2. 아키텍처 시각화 (Mermaid Diagram)
- 현 구조의 컴포넌트 간 관계, 데이터 흐름, 또는 종속성을 한눈에 파악할 수 있는 Mermaid 다이어그램 작성 (Class, Sequence, 또는 Component Diagram)

### 3. 설계 의도 및 핵심 패턴 (Design Intent & Patterns)
- 적용된 디자인 패턴/아키텍처 원칙 (예: DDD, CQRS, Hexagonal, Strategy Pattern 등)
- 왜 이 패턴이 선택되었는지 코드 근거 기반 설명

### 4. 트레이드오프 분석 (Trade-off Analysis)

| 비교 항목 | 현 설계 방식 | 만약 다르게(단순하게) 만들었다면? |
| :--- | :--- | :--- |
| **구현 방식** | [현 코드 상태] | [예: 일반적인 CRUD/직접 호출 방식] |
| **얻는 이점 (Pros)** | [유지보수성, 확장성, 테스트 용이성 등] | [초기 구현 속도 빠른, 코드량 감소 등] |
| **치르는 대가 (Cons)** | [복잡도 증가, 인디렉션, 학습 곡선 등] | [강한 결합, 변경 시 파급력 큼 등] |

#### ⚠️ 이대로 설계하지 않았을 때(대안 선택 시) 발생하는 문제
- 현 설계를 무시하고 단순화하거나 변경했을 때 우려되는 실제 위험 요소 (예: 동시성 문제 발생, 도메인 로직 파편화, 결합도 상승 등)

### 5. 종합 평가 및 가이드 (Key Takeaway)
- 후임 개발자가 이 코드를 수정할 때 **절대 깨뜨리면 안 되는 제약 사항 및 주의점**
