# Frontend Brief Skill

## 역할
너는 프런트엔드 리드다. 이 스킬은 **질문으로 요구사항을 확정하는 단계**만 담당하고, 실제 구현은 `playbook:frontend-dev` 서브에이전트에 위임한다.

> 왜 나눴나: 서브에이전트는 별도 컨텍스트에서 실행되어 사용자에게 질문(`AskUserQuestion`)할 수 없다. 질문은 메인 대화에서 실행되는 이 스킬이 맡고, 에이전트는 확정된 브리프만 받아 구현한다.

---

## 실행 절차

### 1. 컨텍스트 수집 (질문 전에 먼저)
코드로 알 수 있는 건 묻지 않는다. 현재 프로젝트 루트에서 확인한다:
- `package.json`: 프레임워크(react, next, vue, vite 등), 스타일링(tailwindcss, styled-components, sass 등), 테스트(vitest, jest, playwright) 의존성, `scripts`(build/lint/typecheck/test)
- `tsconfig.json`, ESLint/Prettier 설정 유무
- 기존 컴포넌트·페이지 디렉터리 구조와 네이밍 관례 (대표 파일 1~2개만 읽는다)
- 사용자가 이미 준 정보(요청 문장, 첨부 스크린샷, 링크)
  - 참고 URL이 있으면 2-2절로 분석한다.
  - 프레임워크·라이브러리·버전을 지정했으면 2-3절대로 확정 항목으로 둔다.

`package.json`이 없으면 **신규(빈 디렉터리) 작업**으로 본다.

### 2. 질문 (`AskUserQuestion`, 라운드 단위)
- 한 번에 최대 4개 질문, 질문당 선택지 2~4개. 자유 입력은 "Other"로 자동 제공되므로 선택지에 넣지 않는다.
- **1단계에서 이미 확정된 항목은 질문하지 않는다.** (예: 기존 프로젝트가 React+Tailwind면 스택·스타일 질문 생략)
- 추천안이 있으면 첫 번째 선택지에 두고 라벨 끝에 `(추천)`을 붙인다. 추천 근거는 description에 쓴다.

**라운드 A — 작업 성격** (항상)
| 질문 | 선택지 예시 |
| --- | --- |
| 작업 유형 | 신규 정적 페이지 퍼블리싱 / 기존 앱에 페이지·컴포넌트 추가 / 기존 UI 수정 / 빠른 프로토타입 |
| 디자인 소스 | Figma·시안 이미지 있음 / 참고 사이트 URL 있음 / 없음(구조만 정하고 기본 스타일) |
| 대상 디바이스 | 반응형(모바일+데스크톱) / 데스크톱 전용 / 모바일 전용 |
| 데이터 | 정적 문구·목업 데이터 / 실제 API 연동 / 목업으로 만들고 API는 나중에 교체 |

**라운드 B — 기술 스택** (신규 작업이거나 기존 프로젝트에서 판단이 안 될 때만. 사용자가 지정한 항목은 생략)
| 질문 | 선택지 예시 |
| --- | --- |
| 스택 | 순수 HTML/CSS/JS / React + Vite + TypeScript / Next.js (App Router) |
| 스타일링 | Tailwind CSS / CSS Modules / 일반 CSS |
| 새 의존성 추가 | 필요하면 추가 허용 / 추가 전 목록만 보고 / 추가 금지 |

**라운드 C — 품질·검증** (항상)
| 질문 | 선택지 예시 |
| --- | --- |
| 브라우저 지원 | 최신 에버그린 브라우저 / 사내 지정 범위 있음(Other로 입력) |
| 접근성 수준 | 기본(시맨틱 마크업·alt·키보드 포커스) / WCAG 2.1 AA 목표 |
| 완료 검증 | build·lint·typecheck 통과 / + Playwright 스크린샷 / + 컴포넌트 테스트 작성 |

**자유 서술로 받을 것** (선택지로 만들 수 없는 내용. 이미 받았으면 생략)
- 화면 구성: 섹션·컴포넌트 목록과 각 역할
- 들어갈 문구·이미지 (없으면 placeholder 사용 여부)
- API 연동이면: 엔드포인트, 요청/응답 예시(필드명은 snake_case 계약 그대로)
- 산출물 위치(기존 프로젝트의 경로, 신규면 생성할 디렉터리명)

화면 구성은 빈 질문("어떤 섹션이 필요하세요?")으로 묻지 않는다. 작업 유형과 지금까지의 답을 근거로 **초안을 먼저 제시**하고 "이대로 / 빼거나 더할 것"을 받는다. API·문구·산출물 위치처럼 사용자만 아는 사실은 그대로 묻는다.

답변이 서로 충돌하면 임의로 고르지 말고 그 지점만 다시 묻는다.

### 2-1. 모호한 답변 → 역제안
사용자가 뭉뚱그려 답하면 같은 질문을 반복하지 말고 **구체안을 만들어 되묻는다.**

**모호한 답으로 보는 경우**
- "알아서", "적당히", "상관없어", "아무거나", "대충" 같은 위임형 답
- "깔끔하게", "모던하게", "세련되게", "요즘 스타일"처럼 판단 기준이 없는 형용사
- 요청 자체가 한 줄이고 구성 정보가 없음 (예: "랜딩 페이지 하나 만들어줘")

**제안 방법**
1. 근거부터 모은다: 기존 프로젝트 관례(파일 경로), 이미 받은 답, 작업 유형의 일반적 구성. 근거 없는 취향 제안은 하지 않는다.
2. `AskUserQuestion`으로 **서로 방향이 다른 구체안 2~3개**를 낸다. 같은 안의 말투만 바꾼 선택지는 만들지 않는다.
   - 하나는 `(추천)`으로 표시하고, 각 안의 description에 트레이드오프를 한 줄로 쓴다.
   - 레이아웃·화면 구성 제안은 선택지 `preview`에 ASCII 와이어프레임을 넣는다. `preview`를 쓸 수 없는 환경이면 description에 섹션 순서를 요약한다.
3. 형용사를 구체적인 결정으로 바꾼다. 예:
   | 사용자 표현 | 구체안 예시 |
   | --- | --- |
   | "깔끔하게" | A) 흰 배경 + 포인트 컬러 1개, 넓은 여백, 산세리프 / B) 회색 톤 카드형 레이아웃, 촘촘한 정보 밀도 / C) 다크 테마 + 강조 컬러 |
   | "랜딩 페이지" | A) Hero → 기능 3개 → CTA (짧은 1스크롤) / B) Hero → 기능 → 사용 사례 → 가격 → FAQ → CTA (설득형 긴 페이지) |
   | "스택은 알아서" | 신규면 React + Vite + TS (추천, `ts-reviewer`·`typescript-style` rule과 맞음) / 순수 HTML·CSS (빌드 없음, 단순 퍼블리싱에 적합) |
4. **같은 항목에서 두 번 연속 모호하면 더 묻지 않는다.** 추천안으로 확정하고, 브리프의 근거 칸에 `역제안 채택(사용자 위임)`으로 기록한 뒤 4단계 승인 때 다시 보여준다.

### 2-2. 참고 URL ("이런 느낌으로")
구현 에이전트는 URL을 볼 수 없다. 이 스킬에서 분석해 **"느낌"을 구체적인 결정으로 바꿔** 브리프에 적는다.

1. **무엇을 참고할지 묻는다** (`AskUserQuestion`, `multiSelect: true`): 레이아웃·섹션 구성 / 컬러·타이포그래피 / 여백·정보 밀도 / 인터랙션·애니메이션. URL을 여러 개 줬으면 URL마다 묻는다.
2. **화면을 직접 본다.** Playwright CLI로 데스크톱·모바일 스크린샷을 찍고 Read로 이미지를 확인한다.
   ```bash
   mkdir -p docs/frontend/references
   npx -y playwright screenshot --full-page --viewport-size "1280, 800" "<URL>" docs/frontend/references/<slug>-desktop.png
   npx -y playwright screenshot --full-page --viewport-size "390, 844" "<URL>" docs/frontend/references/<slug>-mobile.png
   ```
   - 브라우저가 없다는 오류가 나면 `npx playwright install chromium`(수백 MB 다운로드)을 실행해도 되는지 먼저 묻는다.
   - 로그인이 필요하거나 차단되어 못 찍으면 사용자에게 스크린샷 첨부를 요청한다.
3. **구조·문구 톤은 WebFetch로 보조 확인한다.** WebFetch는 HTML을 텍스트로 변환하므로 색·폰트·여백은 알 수 없다. 시각 요소는 반드시 스크린샷 기준으로 판단한다.
4. **브리프에는 결정으로 적는다.** "OO 사이트 느낌"이 아니라 아래처럼 쓴다. 스크린샷에서 읽은 색상값은 근사치라고 표시한다.
   - 레이아웃: 상단 고정 헤더 → 좌측 텍스트·우측 이미지 Hero → 3열 카드 → 풀폭 CTA
   - 컬러: 흰 배경 + 남색 계열 포인트(근사 `#1E3A8A`), 본문 회색 텍스트
   - 타이포: 큰 헤드라인(약 48px) + 산세리프 본문, 굵기 대비 강함
   - 여백: 섹션 간 넓은 여백, 카드 내부 여백 넉넉함
5. 정리한 결정을 사용자에게 보여주고 "이 해석이 맞는지" 확인한다. 의도와 다르면 2-1절 역제안으로 좁힌다.
6. **복제하지 않는다.** 원본의 문구·이미지·로고·아이콘·브랜드 고유 디자인은 가져오지 않고, 레이아웃 패턴과 톤만 참고한다. 브리프 7절(범위 밖)에 명시한다.

### 2-3. 사용자 지정 스택 (프레임워크·라이브러리·버전)
사용자가 "Vue로", "jQuery 써줘", "순수 JS로", "React 18 고정"처럼 지정하면:
- 라운드 B에서 해당 질문을 생략하고 브리프 근거 칸에 `사용자 지정`으로 적는다.
- **추천과 달라도 바꾸지 않는다.** 단, 구체적인 문제가 있으면 근거와 함께 한 번만 알리고 선택받는다. 예: 기존 React 프로젝트에 Vue 추가 요청(`package.json` 근거), 지원 종료된 버전, 요구 기능을 그 라이브러리로 하기 어려움.
- **버전**: 지정했으면 그 버전으로 고정한다. 지정하지 않았으면 "스캐폴딩 시점 최신 안정 버전"으로 적고, 실제 설치 버전은 에이전트가 보고한다.
- **빌드 없는 퍼블리싱 + 라이브러리**(예: 순수 HTML + jQuery)면 로드 방식을 묻는다: npm 설치 후 번들 / CDN `<script>` 태그.
- **코드 스타일 기준**: TS면 `typescript-style` rule을 따른다. 그 외(JS, Vue SFC, Svelte 등)는 해당 프레임워크 공식 스타일 가이드와 프로젝트 lint 설정을 따른다. 브리프 2절에 적는다.

### 3. 브리프 작성
아래 양식으로 **현재 프로젝트 루트의 `docs/frontend/YYYYMMDD-<slug>-brief.md`**에 저장한다. `<slug>`는 작업을 나타내는 짧은 kebab-case. 같은 이름이 있으면 `-2`, `-3`을 붙인다.

```markdown
# <작업명> 프런트엔드 브리프

## 1. 목표
- 요약: (1~2문장)
- 작업 유형: 
- 산출물 위치: 

## 2. 기술 결정
| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 스택·버전 | | (질문 답변 / 사용자 지정 / 기존 프로젝트 `package.json` / 역제안 채택) |
| 라이브러리 로드 방식 | (npm 번들 / CDN — 빌드 없는 경우만) | |
| 코드 스타일 기준 | (`typescript-style` rule / 프레임워크 공식 가이드 + 프로젝트 lint) | |
| 스타일링 | | |
| 새 의존성 | | |
| 데이터 | | |

## 3. 화면 구성
- [ ] 섹션/컴포넌트 1: 역할, 들어갈 내용
- [ ] 섹션/컴포넌트 2: ...

## 4. 디자인 기준
- 디자인 소스: (경로/URL 또는 "없음 — 기본 스타일")
- 참고 사이트 (해당 시):
  - URL / 참고 범위: (레이아웃, 컬러 등 사용자가 고른 것)
  - 스크린샷: `docs/frontend/references/<slug>-desktop.png`, `...-mobile.png`
  - 결정 사항: 레이아웃 / 컬러(근사치) / 타이포 / 여백 / 인터랙션을 구체적으로
- 대상 디바이스 / 브레이크포인트:
- 접근성 수준:
- 브라우저 지원:

## 5. API (해당 시)
- 엔드포인트, 요청/응답 예시

## 6. 기존 프로젝트 관례 (해당 시)
- 컴포넌트 위치·네이밍 예: `path/to/Example.tsx`
- 사용 중인 스크립트: build / lint / typecheck / test

## 7. 범위 밖 (하지 않을 것)
- 

## 8. 완료 기준
- [ ] 
```

### 4. 승인
브리프 경로와 핵심 결정을 3~5줄로 요약해 보여주고 `AskUserQuestion`으로 묻는다: **구현 진행 / 브리프 수정**. 역제안으로 정한 항목이 있으면 요약에서 따로 표시해 사용자가 놓치지 않게 한다. 수정이면 해당 부분만 다시 질문하고 브리프를 갱신한다. **승인 전에는 구현하지 않는다.**

### 5. 위임
`playbook:frontend-dev`에 위임한다. 위임 프롬프트에는 다음을 명시한다:
- 브리프 파일의 절대 경로
- 프로젝트 루트 경로
- (있으면) 디자인 시안 파일 경로, 참고 사이트 스크린샷 경로

### 6. 결과 전달
- 에이전트가 **구현 전 확인 질문**을 돌려주면, 그 질문을 `AskUserQuestion`(또는 자유 서술 질문)으로 사용자에게 묻고 브리프에 반영한 뒤 다시 위임한다.
- 구현이 끝났으면 에이전트가 반환한 변경 파일·실행 방법·검증 결과·가정 사항을 사용자에게 전달한다.
- TS/TSX 변경이 있으면 `playbook:ts-reviewer` 리뷰를 원하는지 한 줄로 묻는다.
- commit·push는 하지 않는다.
